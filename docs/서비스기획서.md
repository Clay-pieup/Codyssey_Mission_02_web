## 0. 이 문서의 전제 — 공개 범위

이 프로젝트는 **Public GitHub 저장소**로 제출되며 동료 평가자를 포함해 누구나 볼 수 있다.
그래서 이 서비스는 **독립된 이름 `Instay`를 쓰고, 어떤 실제 사업체의 영업 정보도 담지 않는다.**

| 담는 것 | 담지 않는 것 |
|---|---|
| 숏폼 촬영 현장의 문제의식 | 특정 회사·서비스의 상호와 브랜드 |
| 서비스 흐름(개념 수준) | 요금제·수수료·정산 비율 |
| FAQ 성격의 일반 안내 문구 | 시장 규모 추정치·매출 데이터 |
| 직접 생성한 이미지 자산 | 실제 계약 숙소·고객사 실명 |

**왜 이걸 0번에 두었나**
공개 범위는 다 만든 뒤에 정할 수 없다. 한 번 커밋되면 나중에 파일을 지워도 과거 커밋을 되짚으면 내용이 그대로 보이기 때문이다.
API 키를 `.gitignore`로 **먼저** 막아 둔 것과 같은 원리다 — 되돌릴 수 없는 것은 앞에서 막는다.

## 1. 서비스 개요

- **서비스명**: Instay (in + stay — 숙소 안에서 무엇을 담을지 정한다는 뜻)
- **한 줄 소개**: 숏폼 크리에이터가 숙소 촬영을 나가기 전에, 무엇을 어떻게 찍을지 AI로 정리받는 페이지
- **배포 URL**: *(U3에서 확정)*

## 2. 문제 정의와 목적

**문제**
숙소 협찬(체험단) 영상을 찍는 크리에이터는 현장에서 "뭘 찍어야 하지"를 즉흥으로 결정하는 경우가 많다.
그 결과 ① 찍고 와서 보면 빠진 컷이 있고 ② 영상마다 구성이 제각각이라 성과를 비교할 수 없다.

**목적**
촬영 전에 **장면 목록과 캡션 초안**을 30초 만에 손에 쥐게 한다.
숙소 정보 몇 줄만 넣으면 되고, 결과는 그대로 촬영 체크리스트로 쓸 수 있어야 한다.

## 3. 타겟 사용자

- 1차: 숙소 협찬 촬영을 하는 숏폼 크리에이터 (팔로워 규모 무관)
- 상태: 촬영 전날 또는 이동 중. **모바일에서 열어 본다** → 반응형이 선택이 아니라 필수인 이유
- 이 사람이 원하는 것: 완벽한 기획서가 아니라 "빠뜨리지 않을 목록"

## 4. 페이지 구성 (확정)

**파일 2개 구성 (하이브리드)**

### `index.html` — 소개 페이지 (섹션 3개)
| 섹션 | id | 내용 | 목적 |
|---|---|---|---|
| 히어로 | `#home` | 헤드라인 + 한 줄 소개 + 「촬영 가이드 만들기」 버튼 | 여기가 뭐 하는 곳인지 3초 안에 |
| 이렇게 씁니다 | `#how` | 3단계 흐름 (숙소 정보 입력 → 가이드 생성 → 촬영 체크리스트로 사용) | 쓰기 전 불안 해소 |
| 자주 묻는 질문 | `#faq` | 4~6문항 | 분량 보강 + 신뢰 |

### `guide.html` — AI 기능 페이지
입력 폼 + 결과 표시 영역. 이 서비스의 존재 이유.

### 네비게이션
상단 고정 메뉴 4개: `홈` / `이렇게 씁니다` / `자주 묻는 질문` / `촬영 가이드 만들기`
- 앞의 3개는 `index.html` 안의 위치로 이동(`#home` 등)
- 마지막 1개는 `guide.html`로 **주소가 실제로 바뀌는 페이지 이동**
- 모바일에서는 세로로 접힘

**왜 파일 2개인가 (버린 안과 이유)**
- *파일 1개 안*: 제일 쉽지만, AI 기능 코드가 소개 페이지 코드와 한 파일에 섞인다. U5~U8에서 계속 손대야 하는 부분이라 파일이 길어질수록 고칠 곳을 찾기 어려워진다. 버림.
- *파일 4개 안*: 구조는 제일 깔끔하지만, 바닐라 HTML에는 공통 메뉴를 자동으로 넣어 주는 장치가 없다. 메뉴를 한 번 고치면 파일 4개를 다 고쳐야 하고, 한 곳을 빠뜨리면 그 페이지만 메뉴가 다른 상태가 된다. 버림.
- *파일 2개 안(채택)*: 메뉴 복붙은 2곳뿐이고, 자주 고칠 AI 기능은 독립 파일에 격리된다. 주소가 바뀌는 페이지 이동도 1개 확보돼 "페이지 이동"을 설명할 수 있다.

## 5. AI 기능 (확정) — 촬영 가이드 생성기

과제 요건상 최소 1개. 이 서비스에서는 이것 하나다.

### 입력
| 항목 | 형태 | 필수 | 예시 |
|---|---|---|---|
| 숙소 유형 | 선택 (드롭다운) | O | 풀빌라 / 독채 / 호텔 / 펜션 / 캠핑·글램핑 |
| 숙소 특징 | 자유 텍스트 (1~2줄) | O | "바다 바로 앞, 개별 스파, 반려견 동반 가능" |
| 영상 톤 | 선택 (드롭다운) | O | 감성 / 정보 / 유머 |

### 출력
1. **촬영 장면 5컷** — 각 컷마다 `무엇을 / 어떤 앵글로 / 몇 초` 형태의 짧은 문장
2. **숏폼 캡션 초안** 1개
3. **해시태그** 5개

### 사용자에게 주는 가치
촬영장에서 즉흥으로 판단하던 일을, 출발 전 체크리스트로 바꾼다. 빠진 컷 없이 돌아온다.

### 왜 이 기능인가 (버린 안과 이유)
- *숙소 소개 문구 생성기*: 출력이 문단 3개라 만들기는 제일 쉽지만, "문구 써주는 AI"는 흔해서 서비스 자체의 이유를 설명하기 어렵다. 버림.
- *협찬 제안 메일 초안 생성기*: 입력 항목이 많아 테스트할 때마다 다 채워야 해서 개발 중 반복 확인이 번거롭다. 버림.
- *촬영 가이드 생성기(채택)*: 출력이 `5컷 목록 / 캡션 / 해시태그` 세 덩어리로 **모양이 미리 정해져 있다.** AI가 무슨 말을 하든 화면에 뿌리는 코드는 같은 자리에 들어간다. 출력 구조가 고정되면 화면 코드가 단순해진다는 것이 선택의 핵심 이유다.

### AI에게 요구할 응답 형식
AI는 자유롭게 말하려는 성질이 있어서, 그대로 두면 매번 다른 모양의 글이 온다. 그러면 화면에 뿌릴 수가 없다.
→ **JSON 형식으로 달라고 요구한다.** JSON은 "이름표: 값" 짝으로 된 데이터 표기법으로, 컴퓨터가 어느 부분이 캡션이고 어느 부분이 해시태그인지 구분할 수 있게 해 준다.

```
{
  "scenes": ["...", "...", "...", "...", "..."],
  "caption": "...",
  "hashtags": ["...", "...", "...", "...", "..."]
}
```

*(U7에서 실제 프롬프트 확정. A2-02에서 Gemini에 `response_mime_type: application/json`을 걸어 같은 방식을 쓴 경험이 있다.)*

## 6. 실패 처리 기준

AI 응답은 실패할 수 있다. **실패했을 때 화면이 아무 말도 하지 않는 것이 최악**이므로 세 경우를 나눠 다룬다.

| 상황 | 판단 근거 | 화면에 띄울 문구 | 어디서 막는가 |
|---|---|---|---|
| 빈 입력 | 필수 항목이 비었거나 공백만 있음 | "숙소 특징을 한 줄 이상 입력해 주세요." | **브라우저**에서 즉시 (서버까지 안 감) |
| API 오류 | 서버 응답 4xx / 5xx | "지금 가이드를 만들 수 없습니다. 잠시 후 다시 시도해 주세요." | 서버 응답을 받고 나서 |
| 지연·타임아웃 | 20초 넘게 응답 없음 | "응답이 늦어지고 있습니다. 다시 시도해 주세요." | 브라우저에서 시간을 재서 |

**빈 입력을 브라우저에서 먼저 막는 이유**: 어차피 실패할 요청을 서버로 보내면 AI API 호출 횟수만 소모된다(과금·쿼터). 막을 수 있는 곳 중 가장 앞에서 막는다.

**PDF는 세 가지 중 최소 1개만 요구한다. 그런데 3개 다 하는 이유**:
셋은 원인도 다르고 막는 위치도 다르다. 빈 입력은 요청을 보내기 전에, API 오류는 응답을 받은 뒤에, 타임아웃은 응답이 오지 않는 동안 처리한다. 하나만 하면 나머지 두 경우에 화면이 멈춘 것처럼 보인다.

## 7. 화면에 표시할 상태 4가지

결과 영역은 항상 넷 중 하나다. 이걸 미리 못 박아 두면 U5에서 화면 코드가 단순해진다.

1. **대기** — 아직 아무것도 안 함 (안내 문구)
2. **처리 중** — 버튼 비활성화 + "만드는 중..." 표시
3. **성공** — 결과 표시
4. **실패** — 위 6번의 안내 문구 표시

버튼을 처리 중에 비활성화하는 이유: 사용자가 조급해서 여러 번 누르면 그만큼 AI API가 호출되고 요금이 나간다.
