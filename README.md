## 1. 서비스 개요

- **서비스명**: Instay
- **한 줄 소개**: 숏폼 크리에이터가 숙소 촬영을 나가기 전에, 무엇을 어떻게 찍을지 AI로 정리받는 페이지

- **핵심 AI 기능**: 촬영 가이드 생성기 — 숙소 유형·특징·톤을 입력하면 촬영 장면 5컷 + 캡션 초안 + 해시태그 5개를 생성

### 왜 U3(배포)를 이렇게 앞에 두는가

보통은 다 만들고 마지막에 배포한다. 그런데 이 과제의 백엔드인 Vercel Serverless Functions는 **내 컴퓨터에서 그대로 돌려보기가 번거롭다.** 배포된 환경에서만 정상 동작하는 구조이기 때문이다.

- 마지막에 배포하면 → 문제가 터졌을 때 원인 후보가 수십 개(코드? 폴더 구조? 설정? 키?)로 한꺼번에 쏟아진다.
- 빈 페이지 상태에서 먼저 배포하면 → 그 시점에 확인된 것은 "저장소↔Vercel 연결은 정상"이라는 사실 하나다. 이후 무언가 깨지면 **직전에 내가 바꾼 것**이 범인이다.

또한 과제 목표에 "로컬 환경과 배포 환경의 차이, 배포 후 수정·재배포 흐름 설명"이 명시되어 있다. U3 이후 매 단위마다 재배포하게 되므로 이 흐름을 8번 반복 경험하게 된다.

### U0 — 저장소·폴더 구조 준비  ✅

커밋 `7454bd8` — README.md, .gitignore

**저장소를 새로 만든 이유**
기존 `Codyssey_Mission_02` 저장소에 폴더만 추가하는 방법도 있었다. 버린 이유는 두 가지다.

1. Vercel은 저장소를 통째로 보고 "최상위에 `index.html`과 `api/`가 있다"고 가정한다. 하위 폴더에 넣으면 Root Directory를 따로 지정해야 하고, 설정이 하나 늘면 문제가 생겼을 때 의심할 곳이 하나 늘어난다.
2. `Codyssey_Mission_02`에는 A2-01·A2-02 작업이 서로 다른 브랜치로 진행 중이다. 저장소가 하나면 브랜치 상태도 하나여서, 한쪽에서 브랜치를 바꾸면 다른 쪽 작업 폴더까지 바뀐다. 미션을 섞지 않는 편이 안전하다.


**한 일**
- 로컬 폴더 생성 → `git init` → 첫 커밋 → GitHub `Codyssey_Mission_02_web`(Public)에 push
- `README.md` — 이 문서. 작업 단위 계획 + 제출 체크리스트(A~H) + 작업 기록을 한 파일에 모음
- `.gitignore` — `.env`, `.vercel`, `__pycache__/` 등을 커밋 대상에서 제외

**`.gitignore`를 첫 커밋에 넣은 이유**
API 키는 나중에 `.env` 파일에 넣게 된다. 그런데 `.gitignore`를 나중에 만들면, 그 사이에 `.env`가 한 번이라도 커밋되는 순간 **키가 GitHub 이력에 영구히 박힌다.** 파일을 나중에 지워도 과거 커밋을 되짚으면 값이 그대로 보인다. 그래서 "막을 규칙"을 "막을 대상"보다 먼저 만들어 둔다.
- 과제 제약 F1~F4가 요구하는 것이 정확히 이 지점이다.

**브랜치를 나누지 않기로 한 이유**
A2-01은 브랜치·병합 사용이 평가 항목이라 갈래를 만들었다. 이 미션의 요구는 "커밋 이력을 남긴다"까지이고, Vercel은 `main`을 기본 배포 브랜치로 본다. 갈래를 만들면 "지금 배포된 것이 어느 브랜치인가"를 계속 신경 써야 해서, 얻는 것 없이 헷갈릴 거리만 늘어난다. → `main` 한 줄기로 간다.

### U1 — 서비스 기획서  ✅

산출물: `docs/서비스기획서.md` v1.0

**한 일**
`Instay`라는 서비스를 기획했다. 페이지 구성·AI 기능·실패 처리 기준까지 문서로 확정해, U2부터는 "무엇을 만들지"를 다시 고민하지 않아도 되게 했다.

**주제를 익숙한 영역에서 고른 이유**
숏폼 협찬 촬영은 내가 실무로 다뤄 본 영역이다. 낯선 주제를 고르면 "이 기능이 정말 필요한가"를 스스로 판단할 수 없고, AI가 만들어 준 화면을 그대로 받아들이게 된다. **아는 영역이어야 AI의 결과물이 틀렸을 때 틀렸다고 말할 수 있다.**

**이전에 만든 웹페이지 코드를 재사용하지 않은 이유**
예전에 Next.js로 만들어 둔 랜딩페이지가 있었지만 **코드는 한 줄도 쓸 수 없었다.** Next.js는 React 기반 프레임워크이고, 이 과제는 프레임워크 사용을 금지하기 때문이다.
- 금지 이유는 과제 목표에 있다: "HTML/CSS/JavaScript가 각각 어떤 역할을 하는지 설명할 수 있다". 프레임워크는 이 셋의 경계를 일부러 흐려 편하게 만들어 주는 도구라, 쓰면 그 설명 자체가 불가능해진다.
- 그래서 화면은 전부 새로 짠다. 재사용한 것은 코드가 아니라 **문제의식과 화면 구성 감각**이다.

**공개 범위를 기획 첫 항목으로 둔 이유**
Public 저장소는 동료 평가자를 포함해 누구나 본다. 무엇을 담지 않을지는 다 만든 뒤에 정할 수 없다 — 한 번 커밋되면 파일을 지워도 과거 커밋에 남기 때문이다. API 키를 `.gitignore`로 먼저 막아 둔 것과 같은 원리로, 되돌릴 수 없는 것은 앞에서 막는다.

**확정한 것 3가지와 버린 안**

| 결정 | 채택 | 버린 안과 이유 |
|---|---|---|
| 페이지 구성 | 파일 2개 (`index.html` 3섹션 + `guide.html`) | *1개*: AI 기능 코드가 소개 페이지와 한 파일에 섞여 길어짐 / *4개*: 바닐라에는 공통 메뉴 자동 삽입 장치가 없어 메뉴 수정 시 4곳을 다 고쳐야 함 |
| AI 기능 | 촬영 가이드 생성기 | *문구 생성기*: 흔해서 서비스의 이유를 설명하기 어려움 / *제안 메일 생성기*: 입력 항목이 많아 개발 중 반복 테스트가 번거로움 |
| 실패 처리 | 3종 모두 구현 (PDF는 1종 이상 요구) | 셋은 막는 위치가 다르다 — 빈 입력은 보내기 전, API 오류는 받은 뒤, 타임아웃은 안 오는 동안. 하나만 하면 나머지 두 경우에 화면이 멈춘 것처럼 보임 |

**출력 구조를 미리 고정한 것이 이 단위의 핵심**
AI는 그대로 두면 매번 다른 모양의 글을 준다. 그러면 화면에 뿌릴 수가 없다.
그래서 출력을 `장면 5컷 / 캡션 1개 / 해시태그 5개` 세 덩어리로 못 박고, AI에게 **JSON**(이름표와 값이 짝을 이루는 데이터 표기법)으로 달라고 요구하기로 했다.
→ AI가 무슨 내용을 만들든 화면 코드는 같은 자리에 값을 채워 넣기만 하면 된다. 이 결정 하나가 U5·U7의 난이도를 크게 낮춘다.

### U2 — 프론트 뼈대  ✅

산출물: `index.html`, `guide.html`

**한 일**
페이지 2개의 구조만 만들었다. **CSS는 한 줄도 넣지 않았다.**

**스타일을 일부러 넣지 않은 이유**
과제 목표 1번이 "HTML/CSS/JavaScript가 각각 어떤 역할을 하는지 설명할 수 있다"이다.
셋을 한꺼번에 만들면 무엇이 무엇을 하는지 구분되지 않는다. 그래서 순서를 나눴다.

- **U2 (지금)** — HTML만. 화면은 흑백에 글자만 나온다. 이 상태가 **HTML이 담당하는 전부**다: 무슨 내용이 어떤 순서로, 어떤 관계로 있는지.
- **U4** — CSS 추가. 같은 HTML인데 보기 좋아진다. 늘어난 것이 **CSS가 담당하는 부분**이다: 색·크기·배치.
- **U5** — JavaScript 추가. 버튼을 누르면 화면이 바뀐다. 이것이 **JavaScript가 담당하는 부분**이다: 사용자 행동에 반응해 내용을 바꾸는 것.

세 단계를 거치면 "각각 어떤 역할인가"를 말이 아니라 **직접 본 경험으로** 답할 수 있다.

#### 핵심 코드 라인별 해설

##### 1. `<head>` 안의 네 줄 — 화면에 안 보이지만 없으면 망가지는 것들

```html
<!DOCTYPE html>
<html lang="ko">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
```

**`<!DOCTYPE html>`**
브라우저에게 "이 문서는 현대 HTML 규칙으로 읽어라"라고 알리는 선언. 없으면 브라우저가 옛날 방식(호환 모드)으로 해석해서, CSS를 넣었을 때 크기 계산이 미묘하게 어긋난다. U4에서 원인 모를 레이아웃 문제로 나타났을 것이다.

**`lang="ko"`**
이 문서가 한국어라는 표시. 화면 번역 기능과 화면 낭독기(시각장애인용)가 이 값을 보고 동작을 정한다.

**`<meta charset="UTF-8">`**
글자를 어떤 규칙으로 저장했는지 알린다. UTF-8은 전 세계 문자를 담는 표준 규칙이다.
→ **이게 없으면 한글이 `ìëíì` 같은 깨진 글자로 나온다.** 파일에는 한글이 제대로 들어 있는데도 그렇다. 파일이 잘못된 게 아니라, 브라우저가 다른 규칙으로 해석해서 생기는 문제이기 때문이다.

**`<meta name="viewport" ...>` ← 이 줄이 U4의 성패를 가른다**
모바일 브라우저는 기본적으로 "이 페이지는 PC용이겠지"라고 가정하고, **넓은 화면인 척한 뒤 전체를 축소해서** 보여준다. 그래서 글자가 개미만 하게 나온다.
이 줄은 그 가정을 끄는 스위치다. `width=device-width` = "화면 너비를 기기 실제 너비로 잡아라", `initial-scale=1.0` = "처음에 확대·축소하지 마라".
→ **이 줄이 없으면 U4에서 반응형 CSS를 아무리 잘 짜도 모바일에서 데스크톱 축소판으로 보인다.** CSS 문제로 착각하고 몇 시간을 날리기 쉬운 지점이라, 뼈대 단계에서 미리 넣었다.

##### 2. 메뉴 링크 — `#` 하나로 동작이 완전히 달라진다

```html
<a href="#how">이렇게 씁니다</a>          <!-- 같은 문서 안에서 이동 -->
<a href="guide.html">촬영 가이드 만들기</a>  <!-- 다른 파일로 이동 -->
```

**`href="#how"`** — `#`은 "이 문서 안에서 `id`가 `how`인 곳"이라는 뜻이다. 목적지는 아래 줄이다.

```html
<section id="how">
```

`id`는 문서 안에서 **딱 하나뿐인 이름표**다. 같은 `id`를 두 곳에 붙이면 브라우저는 첫 번째만 찾고 멈춘다.
누르면 주소창이 `.../index.html#how`로 바뀌지만 **페이지를 새로 불러오지는 않는다.** 이미 있는 문서 안에서 스크롤만 이동한다.

**`href="guide.html"`** — 파일 이름만 적으면 "지금 이 파일과 같은 폴더의 그 파일"이라는 뜻이다(상대 경로). 이건 **진짜 페이지 이동**이라, 브라우저가 새 파일을 받아 화면을 처음부터 다시 그린다.

→ 메뉴 4개 중 3개는 스크롤 이동, 1개만 페이지 이동이다. 주소창과 새로고침 여부로 둘을 구분할 수 있다.

##### 3. `guide.html`의 메뉴만 다르게 쓴 이유

```html
<!-- index.html -->
<a href="#how">이렇게 씁니다</a>

<!-- guide.html -->
<a href="index.html#how">이렇게 씁니다</a>
```

`#how`는 "**지금 보고 있는 문서 안**의 how"라는 뜻이다. `guide.html`에는 `id="how"`가 없으니 아무 데도 못 간다.
그래서 "index.html 파일로 간 다음, 그 안의 how 위치로"라고 파일명을 앞에 붙여야 한다.

##### 4. `<div>` 대신 `<nav>`, `<section>`, `<footer>`를 쓴 이유

화면에 보이는 결과는 `<div>`를 써도 똑같다. 그런데 태그 이름 자체가 **역할을 설명**한다.
- `<nav>` = 메뉴 영역, `<section>` = 하나의 주제 묶음, `<footer>` = 맨 아래 정보
- 검색엔진과 화면 낭독기가 이 이름을 보고 페이지 구조를 파악한다
- 나중에 코드를 다시 볼 때, `<div>`가 스무 개 있는 것보다 이름이 붙어 있는 편이 찾기 쉽다

##### 5. 지금 감수하고 있는 문제 — 메뉴 복붙

메뉴 4줄이 `index.html`과 `guide.html`에 **똑같이 두 번** 들어가 있다.
메뉴를 하나 추가하려면 두 파일을 다 고쳐야 하고, 한쪽을 빠뜨리면 그 페이지만 메뉴가 다르게 보인다.

바닐라 HTML에는 공통 조각을 자동으로 끼워 넣는 장치가 없다. 이걸 해결하는 것이 React 같은 프레임워크가 하는 일 중 하나인데, 이 과제는 프레임워크를 금지한다.
→ 그래서 **파일을 2개로 제한하는 방식으로 대응**했다(U1의 페이지 구성 결정). 4개였다면 복붙이 4곳이 된다. 문제를 없앤 게 아니라, 감당 가능한 크기로 묶어 둔 것이다.

### U3 — 첫 배포 (Vercel 연결)  ✅

배포 주소: <https://instay-beta.vercel.app/>

**한 일**
Vercel에 새 프로젝트를 만들고 GitHub 저장소 `Codyssey_Mission_02_web`을 연결했다.
**CSS도 JavaScript도 없는, 흑백 글자만 있는 상태 그대로 배포했다.**

**다 만들고 배포하지 않고, 뼈대 상태에서 먼저 배포한 이유**
배포는 내 코드 말고도 여러 가지가 맞물려야 성공한다 — 저장소 연결, 접근 권한, 빌드 설정, 폴더 위치, 나중엔 환경 변수까지.
다 만든 뒤에 한꺼번에 연결하면, 화면이 안 뜰 때 **의심할 곳이 대여섯 군데로 한꺼번에 늘어난다.** 어디부터 봐야 할지 모르는 상태가 된다.

지금 배포에 성공했다는 것은 이 사실 하나를 확정한 것이다: **저장소 → Vercel 경로는 정상이다.**
이후 U4~U8에서 무언가 깨지면, 범인은 **직전에 내가 바꾼 것**이다. 확인해야 할 곳이 항상 한 곳으로 좁혀진다.

덤으로, 앞으로 매 단위마다 push → 자동 재배포 → 배포 주소에서 확인을 반복하게 된다. 과제 목표의 "배포 후 수정·재배포 흐름"이 따로 연습하지 않아도 8번 쌓인다.

#### `file:///` 와 `https://` — 로컬 환경과 배포 환경의 차이

U2까지는 `index.html`을 더블클릭해서 확인했다. 그때 주소창에 뜬 것은 이랬다.

```
file:///C:/Users/.../Codyssey_Mission_02_web/index.html
```

배포 후에는 이렇다.

```
https://instay-beta.vercel.app/
```

앞의 `file:` 와 `https:` 는 **브라우저가 파일을 가져오는 방식**을 가리킨다.

| | `file:///` | `https://` |
|---|---|---|
| 파일을 어디서 가져오나 | 내 컴퓨터 디스크에서 직접 | 인터넷 너머 서버에 요청해서 |
| 누가 볼 수 있나 | 나만 | 주소를 아는 누구나 |
| 서버가 있나 | **없다** | 있다 |

**셋째 줄이 이 과제의 핵심이다.**
`file:///`은 서버가 아예 존재하지 않는다. 그냥 파일을 열어 본 것뿐이다.
그런데 U6부터 만들 AI 기능은 `fetch('/api/generate')` 같은 코드로 **서버에게 요청을 보낸다.** 서버가 없는 곳에서 서버를 부르니 당연히 실패한다.

→ 그래서 U6 이후로는 **AI 기능 확인을 반드시 배포 주소에서 한다.** 이걸 모르면 "내 컴퓨터에서는 안 되는데 왜 안 되지"를 코드에서 찾다가 시간을 버린다. 코드가 틀린 게 아니라 **실행되는 환경이 다른 것**이다.

이것이 U3을 앞으로 당긴 두 번째 이유이기도 하다. 배포 주소가 없으면 U6부터는 확인할 방법 자체가 없다.

필요하지 않은 설정 파일을 미리 두면, 나중에 배포가 잘못됐을 때 **원인 후보가 하나 늘어난다.** 정말 필요해지는 시점에 이유와 함께 추가한다.

### U4 — 스타일 + 반응형  ✅

산출물: `css/style.css` (161줄) — 톤은 에어비앤비 참고(흰 배경, 큰 여백, 둥근 모서리, 코랄 강조색)

**한 일**
CSS 파일을 새로 만들고, 두 HTML 파일에 **각각 한 줄씩만** 추가했다.

```html
<link rel="stylesheet" href="css/style.css">
```

**HTML 내용은 한 글자도 바꾸지 않았다.** 문단도, 제목도, 순서도 그대로다. 그런데 화면은 완전히 달라졌다.
→ 이것이 과제 목표 1번의 답이다. **HTML은 "무엇이 있는가", CSS는 "그것이 어떻게 보이는가"** 를 담당한다. 둘은 파일부터 분리되어 있고, 한쪽만 바꿔도 다른 쪽은 영향을 받지 않는다.

---

#### 핵심 코드 라인별 해설

##### 1. 색을 한 곳에 모아두기 — CSS 변수

```css
:root {
  --brand: #e0565b;
  --text:  #222222;
}
...
nav a:last-child { color: var(--brand); }
```

`--brand` 처럼 `--`로 시작하는 이름을 만들어 두면, 나중에 `var(--brand)`로 꺼내 쓸 수 있다.
`:root`는 "문서 전체"를 가리키는 이름이라, 여기 적어 두면 파일 어디서든 쓸 수 있다.

**왜 이렇게 하는가**: 강조색이 파일 안 여섯 군데에서 쓰인다. 색을 바꾸고 싶을 때 변수가 없으면 여섯 군데를 다 찾아 고쳐야 하고, 하나라도 놓치면 그 부분만 옛날 색으로 남는다. 변수를 쓰면 **고칠 곳이 한 줄**이다.

##### 2. `box-sizing: border-box` — 이게 없으면 레이아웃이 밀린다

```css
* { box-sizing: border-box; }
```

CSS의 기본 규칙에서는 "너비 300px + 안쪽 여백 20px"인 상자의 **실제 크기가 340px**이 된다(양쪽 20px씩 더해짐). 300px인 줄 알고 배치했는데 340px을 차지하니 옆으로 삐져나간다.

`border-box`는 이 계산을 바꾼다. **"너비 300px 안에 여백까지 포함해서 넣어라"** 는 뜻이다. 그러면 300px이라고 적은 것이 실제로 300px을 차지한다.
`*`는 "모든 요소"를 뜻하므로, 이 한 줄로 문서 전체에 같은 규칙을 건다.

##### 3. 가운데 정렬 — `max-width` + `margin: 0 auto`

```css
section, footer, main {
  max-width: 900px;
  margin: 0 auto;
  padding: 48px 20px;
}
```

- `max-width: 900px` — "아무리 넓어져도 900px까지만". 24인치 모니터에서 글이 한 줄에 200자씩 늘어지면 읽기 힘들다.
- `margin: 0 auto` — 위아래 여백 0, **좌우는 `auto`**. `auto`는 "남는 공간을 알아서 나눠 가져라"라는 뜻이고, 양쪽이 같은 값을 가져가므로 결과적으로 가운데 정렬된다.
- `padding: 48px 20px` — 안쪽 여백. 좌우 20px가 있어서 좁은 화면에서 글자가 화면 끝에 닿지 않는다.

##### 4. 숫자를 HTML에 쓰지 않고 CSS가 세게 하기

```css
#how ol { counter-reset: step; }        /* step이라는 계산기를 0으로 */
#how li::before {
  counter-increment: step;              /* 항목마다 1씩 올리고 */
  content: counter(step);               /* 그 값을 글자로 내보낸다 */
}
```

`이렇게 씁니다`의 1·2·3 동그라미 숫자는 **HTML에 적혀 있지 않다.** CSS가 `li`를 세면서 붙인다.

`::before`는 "이 요소의 내용 바로 앞에 가상의 자리를 하나 만들어라"라는 뜻이다. 실제 HTML에는 없는 자리다.

**왜 이렇게 하는가**: 중간에 단계를 하나 추가하면 뒤 번호가 전부 밀린다. HTML에 숫자를 직접 썼다면 그때마다 손으로 고쳐야 하고, 빠뜨리면 `1, 2, 2, 4`가 된다. CSS가 세면 항상 맞는다.

##### 5. 반응형의 전부 — `@media`

```css
/* 기본: 좁은 화면 */
#how ol { display: grid; gap: 16px; }

/* 700px 이상일 때만 추가로 적용 */
@media (min-width: 700px) {
  #how ol { grid-template-columns: repeat(3, 1fr); }
}
```

`@media (min-width: 700px)`는 **"화면 폭이 700px 이상일 때만 이 안의 규칙을 적용해라"** 는 조건문이다.

- `grid`는 요소를 격자로 배치하는 방식이다. 칸 수를 지정하지 않으면 **세로로 한 줄씩** 쌓인다.
- `grid-template-columns: repeat(3, 1fr)` = "세로 칸을 3개 만들고, 남는 공간을 1:1:1로 나눠라". `1fr`의 `fr`은 fraction(비율)이다.

→ 좁은 화면에서는 3단계가 세로로 쌓이고, 넓어지면 가로 3칸이 된다. **HTML은 그대로인 채로.**

##### 6. 모바일을 기본으로 삼은 이유 (버린 안)

반대로 짤 수도 있었다. 넓은 화면을 기본으로 두고 `@media (max-width: 700px)`로 좁을 때를 덮어쓰는 방식이다.

모바일 기준을 기본으로 택한 이유:
1. **기획서에서 정한 타겟이 모바일 사용자다.** 촬영 전날이나 이동 중에 휴대폰으로 여는 사람이다. 기본값은 주 사용자에게 맞추는 게 맞다.
2. **좁은 화면이 제약이 더 크다.** 좁은 화면을 먼저 만들면 꼭 필요한 것만 남기게 되고, 넓어질 때는 여유를 더하기만 하면 된다. 반대로 하면 넓은 화면용으로 만든 것을 좁은 화면에서 하나씩 걷어내야 하는데, 이쪽이 훨씬 어렵다.

##### 7. 지금 확인해야 하는 것 — U2에 넣어 둔 한 줄

U2에서 `<meta name="viewport" ...>` 를 넣어 둔 이유가 여기서 드러난다.
그 줄이 없으면, 위 `@media` 규칙을 아무리 잘 짜도 모바일 브라우저가 **"내 화면은 980px쯤 된다"고 거짓 보고**한다. 그러면 `min-width: 700px` 조건이 참이 되어 **휴대폰에서 가로 3칸 배치가 그대로 나온 뒤 통째로 축소**된다. 글자가 개미만 해진다.
→ viewport 한 줄과 `@media` 한 블록은 **둘이 짝**이다. 하나만 있으면 반응형이 아니다.

#### 이미지를 저장소에 넣지 않고 주소로 불러온 이유 (그리고 그 대가)

두 가지 방법이 있었다.

| | **A. 주소로 불러오기 (채택)** | **B. 파일을 내려받아 `images/`에 넣기** |
|---|---|---|
| HTML | `src="https://images.unsplash.com/..."` | `src="images/pool.jpg"` |
| 저장소 용량 | 늘지 않음 | 사진 4장이면 수 MB |
| 크기 조절 | 주소 뒤 `?w=800`만 바꾸면 됨 | 이미지 편집기로 직접 줄여야 함 |
| **외부 의존** | **Unsplash가 멈추면 사진이 안 뜸** | 없음 — 저장소 안에 있으니 항상 뜸 |
| 배포 대역폭 | Unsplash가 부담 | Vercel이 부담 |

A를 택한 이유는 **크기 조절이 주소 한 줄로 끝나기 때문**이다. Unsplash 원본은 가로 3000px이 넘는다. 그대로 쓰면 휴대폰에서 몇 MB짜리 사진을 받느라 화면이 늦게 뜬다. 주소에 `?w=800&q=70` 을 붙이면 Unsplash 쪽에서 가로 800px, 품질 70%로 줄여서 보내 준다. 파일을 직접 관리했다면 크기별로 여러 벌을 만들어야 했다.

**대가는 외부 의존이다.** 이 페이지는 이제 Unsplash가 살아 있어야 완전하게 보인다. 과제 제출물은 "배포 URL에서 동료가 접속해 확인"하는 것이 요건이므로, 평가 기간 중 사진이 안 뜨면 그대로 감점 요인이다.
→ 그래서 `alt` 속성을 모든 이미지에 넣었다. 사진이 안 뜨면 최소한 **무엇이 있어야 할 자리인지 글자로 보인다.**

*(B로 바꾸는 것은 사진 4장을 내려받아 `images/`에 넣고 `src`를 4줄 고치는 작업이다. 필요해지면 전환한다.)*

#### 핵심 코드 라인별 해설

##### 1. `<img>` 태그에 붙인 속성들

```html
<img class="hero-photo"
     src="https://images.unsplash.com/photo-...?w=1600&q=70&auto=format&fit=crop"
     alt="수영장을 갖춘 리조트를 위에서 내려다본 모습"
     width="1600" height="900">
```

**`alt`** — 사진을 못 볼 때 대신 읽히는 글자다. 시각장애인의 화면 낭독기가 이걸 읽고, 인터넷이 느려 사진이 안 뜰 때도 이게 보인다. 장식용이 아니라 **사진이 실패했을 때의 대비책**이다.

**`width` / `height`** — 사진이 아직 도착하지 않았을 때도 브라우저가 **자리를 미리 비워 두게** 하는 값이다. 이게 없으면 글자를 먼저 그린 뒤 사진이 도착하는 순간 아래 내용이 우르르 밀린다. 읽던 줄이 갑자기 튀는 그 현상이다.
> 여기 적은 숫자는 "이 크기로 그려라"가 아니라 **"가로세로 비율이 이렇다"**는 정보다. 실제 크기는 CSS가 정한다.

**`loading="lazy"`** (갤러리 3장에만) — "화면에 보일 때쯤 불러와라". 갤러리는 스크롤을 내려야 나오니 처음부터 받을 이유가 없다. 히어로 사진은 처음부터 보이므로 붙이지 않았다.

##### 2. 사진이 찌그러지지 않게 하는 두 줄

```css
.photo-grid img {
  aspect-ratio: 1 / 1;   /* 칸을 정사각형으로 */
  object-fit: cover;     /* 그 칸을 꽉 채우되 비율은 유지, 넘치면 잘라냄 */
}
```

사진 3장은 원본 비율이 제각각이다(가로로 긴 것, 세로로 긴 것). 그냥 늘어놓으면 높이가 다 달라 지저분해진다.

- `aspect-ratio: 1 / 1` — 칸을 정사각형으로 고정한다.
- `object-fit: cover` — 사진을 **비율을 유지한 채** 칸에 꽉 차게 확대하고, 칸 밖으로 넘치는 부분은 잘라낸다.

`cover`가 없으면 사진이 칸 모양에 맞춰 **찌그러진다**(가로로 눌리거나 세로로 늘어남). 사람 얼굴이 있는 사진에서 특히 티가 난다.

##### 3. `class`를 처음 쓴 이유

U4까지는 `nav`, `#home` 처럼 **태그 이름**과 **id**만으로 스타일을 걸었다. 여기서 `class="hero-photo"`, `class="photo-grid"` 를 처음 썼다.

- **id(`#home`)** — 문서 안에 **하나뿐**이어야 한다. "그 히어로 영역"처럼 유일한 것을 가리킬 때
- **class(`.photo-grid`)** — **여러 곳에 반복해서** 붙일 수 있다. "사진 격자"라는 종류를 가리킬 때

갤러리는 나중에 다른 페이지에도 같은 모양으로 쓸 수 있어서 class가 맞다. 반대로 히어로 영역은 페이지에 하나뿐이라 id가 맞다.

#### 왜 AI를 아직 안 붙였나 — 이 단위의 존재 이유

버튼을 눌러 결과가 나오기까지는 세 가지가 모두 맞아야 한다.

1. 화면이 입력값을 제대로 읽어오는가
2. 화면이 결과를 제대로 그리는가
3. AI가 제대로 응답하는가

셋을 한꺼번에 만들면, 화면에 아무것도 안 나올 때 **어디가 문제인지 알 수 없다.**
지금 1번과 2번을 가짜 데이터로 먼저 확정했다. 이 상태에서 결과가 잘 나온다는 것은 **화면 쪽은 완성됐다**는 뜻이다.
→ U7에서 AI를 붙였을 때 결과가 안 나오면, 범인은 3번뿐이다.

**핵심 설계: 가짜 데이터의 "모양"을 진짜와 똑같이 맞췄다**

```js
function makeMockGuide(stayType, features, tone) {
  return {
    scenes:   [ ...5개 ],
    caption:  "...",
    hashtags: [ ...5개 ]
  };
}
```

이 모양은 U1 기획서에서 AI에게 요구하기로 정한 JSON 구조와 **동일하다.**
그래서 U7에서 할 일은 이렇게 정리된다.

- `makeMockGuide()` 자리 → 실제 `fetch()` 호출로 교체
- `renderGuide()` → **한 줄도 안 고침**

화면 그리는 코드가 "데이터가 어디서 왔는지" 모르게 만들어 둔 것이 이 단위의 핵심이다.

---

#### 핵심 코드 라인별 해설

##### 1. `event.preventDefault()` — 안 쓰면 화면이 깜빡이고 결과가 사라진다

```js
form.addEventListener("submit", function (event) {
  event.preventDefault();
```

`<form>`은 웹의 오래된 기능이라 **원래 동작이 정해져 있다**: 제출되면 입력값을 주소에 붙여 **페이지를 새로 불러온다.**

그런데 우리는 페이지를 그대로 둔 채 결과만 화면에 추가하려 한다. 기본 동작이 그대로면, 결과를 그리자마자 페이지가 새로고침되어 **화면이 깜빡이고 결과가 사라진다.**
`preventDefault()`는 "브라우저야, 네 기본 동작은 하지 마라"라는 뜻이다.

> `<button>` 클릭이 아니라 `<form>`의 `submit`을 듣는 이유: 이러면 **입력칸에서 엔터를 쳐도** 동작한다. 버튼 클릭만 들으면 엔터로는 아무 일도 안 일어난다.

##### 2. `textContent` — 여기서 `innerHTML`을 쓰면 보안 구멍이 된다

```js
item.textContent = scene;      // 이렇게 썼다
// item.innerHTML = scene;     // 이렇게 쓰면 안 된다
```

둘 다 화면에 글자를 넣는다. 차이는 **글자를 어떻게 해석하는가**다.

- `textContent` — 받은 것을 **글자 그대로** 넣는다. `<b>안녕</b>`을 넣으면 화면에 `<b>안녕</b>`이라고 보인다.
- `innerHTML` — 받은 것을 **HTML 명령으로 해석**한다. `<b>안녕</b>`을 넣으면 굵은 **안녕**이 된다.

결과에는 사용자가 입력한 "숙소 특징"이 섞여 들어간다. 만약 누군가 입력칸에 `<script>...</script>` 같은 것을 적었는데 `innerHTML`로 넣으면, **그 코드가 실제로 실행된다.** 이걸 XSS(교차 사이트 스크립팅)라고 한다.
→ 화면에 글자만 넣을 때는 `textContent`를 쓴다. 이건 취향이 아니라 규칙이다.

> 단, `resultArea.innerHTML = ""` 는 안전하다. 빈 문자열에는 실행될 코드가 없고, "이전 결과를 통째로 비운다"는 뜻으로만 쓰인다.

##### 3. 버튼을 잠그는 이유는 예의가 아니라 돈이다

```js
function showLoading() {
  submitBtn.disabled = true;
  submitBtn.textContent = "만드는 중...";
```

응답을 기다리는 동안 화면이 조용하면 사용자는 "안 눌렸나?" 하고 다시 누른다.
지금은 가짜 데이터라 아무 일도 없지만, **U7 이후에는 누른 횟수만큼 AI API가 호출되고 그만큼 요금이 나간다.**
버튼을 잠그는 것은 과제 제약사항의 "호출 빈도를 고려한다"에 해당하는 실제 조치다.

##### 4. 일부러 넣은 1.2초 지연

```js
setTimeout(function () {
  ...
}, 1200);
```

가짜 데이터는 즉시 만들어지므로, 그냥 두면 "만드는 중" 상태가 **눈에 보이지도 않게** 지나간다. 그러면 그 상태가 제대로 동작하는지 확인할 수 없다.
진짜 AI 호출은 2~5초가 걸리므로, 그 상황을 미리 흉내 내어 흐름을 검증한다.
**U7에서는 이 `setTimeout` 자리가 그대로 `fetch()` 호출로 바뀐다.** 기다리는 구조는 이미 만들어져 있다.

##### 5. `<script>`를 body 맨 끝에 둔 이유

```html
  <script src="js/guide.js"></script>
</body>
```

`guide.js`는 첫 줄부터 `document.getElementById("guide-form")` 로 화면 요소를 찾는다.
브라우저는 HTML을 **위에서 아래로** 읽으므로, `<head>`에 스크립트를 두면 그 시점에는 폼이 아직 만들어지지 않았다. 찾는 데 실패해 `null`이 되고, 그 뒤 코드가 전부 에러로 멈춘다.
→ 찾을 대상이 다 만들어진 뒤에 실행되도록 맨 끝에 둔다.

##### 6. `aria-live="polite"` — 화면을 못 보는 사용자를 위한 한 마디

```html
<section id="result-area" aria-live="polite">
```

화면 낭독기는 보통 페이지가 처음 열릴 때만 내용을 읽는다. 나중에 JavaScript가 채워 넣은 결과는 **읽어 주지 않는다.**
`aria-live="polite"`는 "이 영역의 내용이 바뀌면 (읽던 것을 끝낸 뒤) 알려 줘라"라는 표시다.
"결과가 나왔다"는 사실을 눈으로만 알 수 있게 두지 않기 위한 한 줄이다.

### U5-1 — 상단 바 정비 (로고 + 가운데 메뉴)

**한 일**
- 상단 바 왼쪽에 텍스트 로고 `Instay` 추가 (누르면 홈으로)
- 메뉴 4개를 `<div class="nav-links">` 로 묶어 **가운데 정렬**

**메뉴를 진짜 화면 중앙에 두는 방법**

```css
@media (min-width: 700px) {
  nav { grid-template-columns: 1fr auto 1fr; }
}
```

상단 바를 **세 칸**으로 나눈다: `[로고] [메뉴] [빈 칸]`.
- 양옆 칸의 폭을 `1fr`로 **똑같이** 잡는다 (`fr` = 남는 공간을 나누는 비율)
- 가운데 칸 `auto`는 메뉴에 필요한 만큼만 차지한다

왼쪽 칸과 오른쪽 칸이 항상 같은 폭이므로, 가운데 칸은 **로고 길이와 무관하게 화면 정중앙**에 온다.
→ 만약 세 칸으로 안 나누고 `justify-content: center` 만 썼다면, 로고가 자리를 먹는 만큼 메뉴가 오른쪽으로 밀린다. 로고 글자 수를 바꾸면 그때마다 중앙이 어긋난다.

**좁은 화면에서는 두 줄**
기본값(`display: grid` + `gap: 10px`)에서는 로고와 메뉴가 세로로 쌓인다. 로고는 `justify-self: start`로 왼쪽, 메뉴는 `justify-content: center`로 가운데.
→ 휴대폰에서 로고와 메뉴 4개를 한 줄에 넣으면 글자가 뭉개진다. 두 줄이 맞다.

**U2에서 감수하기로 한 비용이 여기서 실제로 발생했다**
상단 바를 고치는 데 **`index.html`과 `guide.html` 두 파일을 똑같이 수정**해야 했다. U2 작업 기록에 적어 둔 "메뉴 복붙" 문제가 처음으로 실제 작업량이 된 순간이다.
- 파일이 2개라 두 번으로 끝났다. U1에서 페이지를 4개로 나눴다면 네 번이었고, 한 곳을 빠뜨리면 그 페이지만 로고가 없었을 것이다.
- 이것이 React 같은 프레임워크가 해결해 주는 문제다. 과제가 프레임워크를 금지했으므로, **파일 수를 줄이는 방식으로 문제의 크기를 제한**했다.

#### 정정 — `<textarea>`에서 엔터는 줄바꿈이 맞다

U5 확인 항목에 "입력칸에서 엔터를 쳐도 동작하는가"를 넣었는데, **숙소 특징 칸(`<textarea>`)에서는 동작하지 않는 것이 정상이다.**
`<textarea>`는 여러 줄을 쓰라고 만든 칸이라 엔터가 줄바꿈으로 예약되어 있다. 여기서 엔터로 제출되면 두 줄짜리 특징을 적을 수 없다.

`<button>` 클릭이 아니라 `<form>`의 `submit`을 듣는 실제 이점은 다음 두 가지다.
1. 드롭다운(`<select>`)에 포커스가 있을 때는 엔터로 제출된다
2. 나중에 `required` 같은 브라우저 기본 검증을 붙이면 자동으로 연동된다 (U8에서 사용)

*(원한다면 `Ctrl + Enter`로 제출되게 만들 수 있다. 긴 글을 자주 넣는 화면에서 흔히 쓰는 방식이다. 필요하면 U8에서 함께 넣는다.)*
